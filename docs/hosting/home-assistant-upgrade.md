# Перенос HA-форка на upstream — 8 сентября 2026

## Основа и границы переноса

Новая история основана непосредственно на `we-promise/sure`:
`eff81c2dacaa329d57d79ecd3f2815ec5cdd9b9e` (версия `0.7.5-alpha.7`).
До этой точки коммиты идентичны upstream; изменения HA расположены поверх отдельными коммитами.
Исходный main: `3d589c0d18ccdba9f7ddc6b228b76889e17e3f63`, сохранён в `backup/pre-upstream-20260908`.
Переводы взяты из upstream без замены старыми русскими файлами.
Сохранены пользовательские расчёты платежа по текущему остатку и оставшемуся
сроку кредита, среднего расхода родителя с подкатегориями и отображение среднего
вместо медианы в бюджете. Инвалидация агрегатов при изменении категорий объединена
с новой upstream-инвалидацией при удалении операций.

Перенесены авторизация HA, стабильный идентификатор провайдера
`home_assistant_ingress`, прежний алгоритм HA-email, существующие связи пользователей
с семьями, Ingress-префиксы маршрутов, ресурсов и WebSocket, навигация окон, UUID в настройках
панелей, фильтрация категорий по ID и scoped-уникальность названий.
Старые ссылки поиска с `categories[]` остаются совместимыми; новые используют
`category_ids[]` и отдельный токен `__uncategorized__`.
Иерархические QIF/CSV-сопоставления учитывают родителя; неоднозначное плоское имя
не привязывается автоматически к произвольной подкатегории.

Автовход работает только при `SELF_HOSTED=true`, `HA_INGRESS_AUTO_LOGIN=true` и
соединении от Supervisor `172.30.32.2` с `X-Ingress-Path`.
Проверяется socket peer, а не подставляемый `X-Forwarded-For`.
Сохранены новые upstream-блокировки удалённых SSO-идентичностей.
Для запросов через Ingress допускается внешний HA Origin, но CSRF-токены по-прежнему
обязательны. Это соответствует [требованию HA к источнику Ingress](https://developers.home-assistant.io/docs/apps/presentation/#ingress).

Workflow публикации сохраняет актуальную сборку Docker для amd64/arm64 и CI;
автоматизация мобильных/desktop/Helm-релизов не переносится в HA-форк.

В переносе эта версия выполняет только проверку допустимой уникальности и ничего
не объединяет. При настоящих дубликатах внутри одного родителя или дубликатах
тегов миграция останавливается с ошибкой для ручного решения после бэкапа.
Следующая версия `20260727120000` создаёт scoped-индексы категорий вместо
ограничения на имя во всей семье. Исправление должно находиться именно **до**
опасного шага, а не в более поздней компенсирующей миграции.

## Проверка сохранности

Рабочая БД читалась через соединение с `default_transaction_read_only=on`.
`pg_dump -Fc` создан согласованно и восстановлен в отдельный локальный PostgreSQL 17.
На копии выполнены все ожидавшие миграции. Сравнивались все исходные строки и
все исходные поля, включая идентификаторы, категории транзакций, суммы, бюджеты,
пользователей и OIDC-связи. Количества записей и подробный результат находятся
в закрытом локальном отчёте.

Потерянных исходных ID и изменённых финансовых значений нет.
Два предусмотренных upstream преобразования проверены по значениям:
`categories.classification` → `classification_unused`,
`addresses.postal_code` integer → string.
Существующие дополнительные legacy-столбцы в HA не удаляются ради совпадения
с каноническим `schema.rb`. Новые установки используют схему upstream с точечными
изменениями форка; schema load на существующей БД **не применяется**.

После миграций на копии проверены вход существующей HA-идентичности и страницы
главной, счетов, транзакций, категорий, бюджетов, отчётов, профиля.
Это проверка HTTP/Rails, а не визуальный прогон мобильного клиента HA.

## Проверка и последующее обновление дополнения

Публикация main этого репозитория сама по себе не обновляет установленный add-on:
его упаковка находится отдельно в `firmfreez/sure_hass`, имеет собственную версию
и образ `ghcr.io/firmfreez/{arch}-sure_finance_ha`. Рабочая БД в рамках переноса кода не мигрировалась.

Перед фактическим обновлением следует остановить запись Sure (web и sidekiq),
получить свежий PostgreSQL dump и резервную копию storage/options, затем повторить
проверку на отдельной копии. Не менять `POSTGRES_DB`, `SECRET_KEY_BASE`, настройки
шифрования и путь `/data/storage`. Не запускать `db:reset`, `db:drop`,
`db:schema:load` или seed на существующей БД.

Упаковка add-on запускает `bin/rails db:prepare` **до** web и sidekiq. Поэтому
устанавливать можно только образ, содержащий обе исправленные миграции категорий.
Возвращать старый образ после миграций без соответствующего восстановления БД
не следует: некоторые upstream-преобразования необратимы.

Для повторяемой проверки имеется скрипт, который не выводит финансовые значения:

```sh
# Только в окружении изолированной копии, до и после миграций:
bin/rails runner script/ha_upgrade_audit.rb capture /private/path/before.json
bin/rails db:migrate
bin/rails runner script/ha_upgrade_audit.rb capture /private/path/after.json

# Сравнение файлов не подключается к БД:
ruby script/ha_upgrade_audit.rb compare /private/path/before.json /private/path/after.json
```

Capture работает в read-only repeatable-read транзакции и не перезаписывает
существующий файл. Compare завершится ошибкой при потере ID, изменении исходных
полей или удалении старых записей ledger; допустимы только описанные выше
преобразования без потери значений. После обновления нужна отдельная проверка
UI HA: вход, навигация, создание/редактирование операции и вложения.
